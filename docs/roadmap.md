# WeClaw 整体产品与架构规划

更新日期：2026-08-06

## 1. 产品定位

WeClaw 是“个人微信里的本机 Codex 工作台”。它不是通用聊天机器人、多模型路由器，也不是让模型直接控制机器的远程 Shell。产品只围绕四条完整闭环扩展：

1. 输入：微信文字、图片和受限文件安全进入一次 Codex turn。
2. 工作：项目、会话、任务和后续操作拥有明确状态，服务重启后仍可解释。
3. 交付：文字、阅读卡、图片、文件和音频按手机最合适的形式返回。
4. 运维：检查、通知、锁定、升级和回滚由确定性代码完成，不依赖模型猜测。

产品判断标准不是“命令数量”，而是用户能否只靠自然语言、数字选择和少量高频入口完成一次工作。主菜单始终最多四项；高级能力进入领域中心，不扩张成命令墙。

## 2. 当前基线

### 2.1 仓库与生产的真实状态

| 范围 | 2026-08-06 状态 | 结论 |
| --- | --- | --- |
| 仓库 `main` | v2.7 功能代码已完成，P0–P4 自动化门槛通过 | 可以冻结为首次生产候选 |
| 生产运行时 | `v2.5.0-queue.1`，仍使用回环 TCP 管理面与 `start --api-addr` | 尚未获得 v2.6/v2.7 的控制面和工作流能力 |
| 版本发布 | 尚无 v2.x Git tag，现有 tag 仍属于旧产品线 | 必须先形成不可变候选与证据，再建立 v2.7 基线 |
| 真机验收 | P0 已验证；P1–P4 仍需要在首次切换后合并回归 | 不能把“代码完成”等同于“生产完成” |

当前最重要的工作不是继续叠加 P5，而是一次性完成 `v2.5 → 当前 main` 的破坏性切换。当前候选已经在生产状态副本上完成离线迁移演练：旧 `api_addr` 被删除、发送 API 默认关闭、三个旧快捷任务迁入按绑定者隔离的 `workflows.json`，迁移后的真实配置通过 v2.7 严格解析与完整校验。演练没有触碰生产服务，也没有启动第二个微信轮询进程。

### 2.2 已具备的产品能力

| 领域 | 已实现能力 | 尚待生产证明 |
| --- | --- | --- |
| 工作空间 | 项目白名单、项目切换、项目内持久快捷工作流 | 旧配置工作流迁移与真机 CRUD |
| 会话 | 新建、搜索、详情、切换、重命名、归档、恢复 | 重启后的数字菜单续接 |
| 任务 | 持久 FIFO、任务中心、暂停、重排、取消、重试、重启恢复 | 图片/PDF 连续排队与故障恢复 |
| 输入 | 文字、最多四张图片、受限文件、图片批注 | 真机图片和文件链路回归 |
| 输出 | 自适应、阅读、语音三种持久回答方式，五种视觉风格 | 图片 + MP3 配对与超长回答降级 |
| 运维 | Unix 管理面、结构化健康、排空、事务部署、远程锁定、确定性诊断 | 首次人工跨管理面切换与一次真实回滚 |
| 自动化 | 配置式 Git/systemd/HTTP 检查、去重通知、微信查看与手动运行 | 微信内创建、暂停、恢复、删除尚未实现 |

配置中的 `voice.enabled` 表示语音能力可用，并要求视觉渲染同时开启。微信发送“发语音”只触发一次语音简报；“开启语音模式”则持久应用于后续 Codex 回答。微信通道目前不能可靠产生原生语音气泡，因此语音交付固定为阅读图片与 MP3 文件的同批事务，不伪装成原生语音。

## 3. 目标架构

```text
微信输入
  └─ 入站校验与任务私有附件
      ├─ 类型化控制意图
      │    ├─ 项目 / 会话 / 任务
      │    ├─ 工作流 / 偏好 / 收藏
      │    └─ 关注 / 运维 / 安全
      └─ Codex turn
           └─ 单一 App Server 运行时
                └─ 冻结结果
                     └─ 结构化交付计划
                          ├─ 文字
                          ├─ 阅读卡
                          ├─ 交付物
                          └─ 图片 + 音频批次
                               └─ 整批预上传后确定顺序发送
```

架构继续遵守以下边界：

- Codex 只负责理解与生成，控制状态、计划调度、发送事务和升级事务由程序负责。
- 配置只保存机器级信任边界和密钥引用；用户可变内容进入按绑定者隔离的严格状态域。
- 工作流、自动化和收藏只保存完成产品闭环所需的数据，不默认永久保存回答正文。
- 多媒体先冻结内容并完成整批预上传，再开始任何可见发送；不允许功能自行拼接半事务发送。
- 破坏性版本只提供单向离线迁移，不保留旧字段读取、双写、兼容路由或隐藏降级。

## 4. 路线与硬门槛

### G0：建立 v2.7 生产基线

状态：当前唯一阻塞阶段，代码候选与隔离迁移预检已完成，等待维护窗口和真实微信验收。

工作范围：

1. 冻结当前主线，生成带精确版本和 SHA-256 的 Linux 候选；完整执行 race、vet 与双架构构建。
2. 用旧 v2.5 管理面排空并停止服务，独立备份二进制、systemd 单元和完整状态。
3. 只在停服状态运行候选离线迁移，删除单元中的 `--api-addr`，以排空模式启动候选。
4. 通过 Unix socket 验证版本、Codex、微信监控、同步状态、队列和迁移结果，再显式恢复任务领取。
5. 在真实微信完成 P1–P4 合并回归，并至少演练一次“候选失败 → 二进制、单元和完整状态同时恢复”。
6. 连续观察 24–48 小时无持久化、轮询、投递和队列异常后，才把 v2.7 标记为生产基线。

硬门槛：G0 完成前不合入 P5 状态 schema。首次跨越不能由当前 `weclaw deploy` 驱动，因为新 CLI 只理解 Unix socket，而线上 v2.5 只提供 TCP 管理面。具体执行和回滚证据见 [首次生产切换与真机验收](operations/production-cutover.md)。

### P5：v2.8 临时关注与自动化中心

目标：让用户可以说“接下来一天盯住这个服务，异常或恢复时告诉我”，而不是手工编辑配置。

产品范围：

- 微信内创建、查看、立即检查、暂停、恢复、修改和二次确认删除关注。
- 只允许已配置项目上的 `git`、`service`、`health` 检查，不接受自由 Shell、自由 URL 或模型生成的检查器。
- 关注固定包含项目、检查项、触发条件、周期、时区、到期时间和启停状态；临时关注默认 24 小时、最长 7 天。
- 通知支持异常、恢复、变化和始终四类确定性策略；相同指纹不重复发送，多项变化在一个调度窗口合成一张摘要。
- 定义、运行游标、指纹和通知回执按绑定者隔离；主动通知不依赖用户刚好拥有当前会话令牌。

破坏性调整：删除 `config.automations` 作为运行时定义源，把现有配置计划一次性迁入新的严格自动化状态；配置只保留项目的 `service_name` 与 `health_url` 安全边界。旧 `automation-state.json` 不再作为事实来源，不兼容读取或双写。

开发批次：

1. 建立统一自动化定义与运行状态、容量限制、过期回收和离线迁移。
2. 重构调度器为按绑定者运行，补齐异常、恢复、变化、合并与去重状态机。
3. 完成微信 CRUD、分页详情、逐项表单、幂等回执和远程锁定边界。
4. 完成时间推进、崩溃恢复、主动通知和真机四态验收。

完成门槛：一次关注完整经历正常、异常、恢复、暂停、重启和过期；微信可见通知次数、状态文件和调度收据完全一致。

### P6A：v2.9 变更画册与受限预览

目标：把一次编码任务压缩成手机上能迅速理解的高质量交付，而不是把终端日志或原始 diff 塞进卡片。

- 基于任务冻结结果生成 1–3 张确定性变更画册：目标、文件统计、测试结论、交付物与风险。
- 前端项目可以配置允许的本机预览地址；受限浏览器只访问配置的 loopback 地址，禁止任意网络、文件 URL 和脚本桥接。
- 支持任务前后截图与并列对比，捕获失败只影响预览，不改变任务成功状态。
- Codex 如需丰富报告，只能输出受限报告 schema；WeClaw 自行使用当前视觉风格渲染 PNG/PDF，不执行任意 HTML 或 JavaScript。
- 卡片继续统一使用 Lucide 图标，禁止表情符号和低信息量装饰；视觉模板以内容层级、触屏字号和留白质量为验收核心。

完成门槛：同一前端任务返回前后截图、变更画册和可再次发送的交付物；卡片中不存在原始 diff、终端输出、账号、私有路径或凭据。

### P6B：v2.10 显式项目记忆

目标：让用户主动收藏真正需要长期复用的结果，保持默认隐私边界不变。

- 只有用户明确发送“收藏这条”或选择收藏动作，才保存最近一次完整回答、交付引用、来源项目和时间。
- 支持搜索、详情、标签、取消收藏、重新发送交付物和“在新会话继续”。
- 收藏使用独立的按绑定者/项目状态域；工作流仍只保存原始意图，不能退化成回答仓库。
- 删除或过期交付物时更新引用状态，不留下看似可用的伪入口。

完成门槛：收藏内容重启后可检索并继续工作；未收藏回答不会进入长期状态，跨项目和跨绑定者不能读取。

## 5. 版本顺序

| 版本 | 范围 | 进入条件 | 退出条件 |
| --- | --- | --- | --- |
| `v2.7` | P0–P4 合并生产基线 | 当前主线冻结、隔离迁移成功 | 首次切换、真机矩阵、回滚与稳定观察完成 |
| `v2.8` | P5 临时关注与自动化 CRUD | v2.7 生产基线成立 | 四态调度、重启恢复、主动通知真机通过 |
| `v2.9` | P6A 变更画册与受限预览 | v2.8 无通知噪声回归 | 前后截图、画册、报告 schema 安全通过 |
| `v2.10` | P6B 显式项目记忆 | v2.9 交付引用稳定 | 收藏、检索、失效引用与隐私验收通过 |

版本号表达实际生产能力，不再让“仓库已实现”提前占用“版本已交付”的含义。每版只有在代码、迁移、自动化、真实微信和回滚五类证据齐全后才能关闭。

## 6. 后续候选功能

以下能力有价值，但不进入当前关键路径：

| 候选 | 价值 | 前置条件 |
| --- | --- | --- |
| 交付箱 | 集中查看最近图片、文件、报告与失效时间 | P6A 先统一交付引用和冻结结果 |
| 任务订阅 | 长任务只在阶段变化时通知，减少进度噪声 | P5 通知合并与去重状态机 |
| 移动端审查包 | 将改动摘要、测试和关键截图组织成可批注审查包 | P6A 受限报告 schema |
| 项目仪表卡 | 一张卡查看分支、服务、健康、最近任务和关注 | P5 稳定状态模型与 P6A 卡片系统 |
| 本机配置体检 | 离线验证配置、浏览器、TTS、Codex 与 systemd 前提 | v2.7 切换经验固化后独立设计 |

明确不做：多 Agent/多模型路由、任意工作目录、任意 Shell 或 URL 自动化、无人确认的提交/推送/部署、群聊协作、默认永久记忆、伪原生语音气泡、旧斜杠命令和旧 schema 兼容层。

## 7. 功能取舍与验收规则

每个新功能进入开发前必须回答七个问题：

1. 它属于输入、工作、交付或运维哪条闭环？
2. 它能否通过自然语言或四项以内菜单完成？
3. 失败、部分成功和结果不确定时，用户分别看到什么？
4. 重启后状态在哪里，谁拥有，多久过期？
5. 是否需要 `context_token`，主动发送时没有令牌怎么办？
6. 是否扩大项目、网络、文件或凭据边界？
7. 自动化、真实微信和回滚分别如何验收？

任何一项无法确定，就不进入主菜单和持久状态。优先级固定为“交付可靠性 → 核心工作流 → 使用频率 → 隐私与可恢复性 → 视觉精度 → 新奇程度”。
