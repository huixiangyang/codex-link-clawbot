# 可靠控制面架构

## 1. 定位

控制面不扩张 Codex 执行能力，而是把 codex-link-clawbot 请求队列包进一个可审计、可扩展的确定性边界，为全局线程接管、交付箱和后续状态域提供稳定底座。

它解决三个具体问题：

1. 微信意图、数字菜单和领域动作仍集中在大路由中，新增功能容易互相抢词或污染状态。
2. 旧十分钟菜单状态只在内存，服务重启后用户回复数字可能变成普通 Codex 输入。
3. 各领域重复实现严格 JSON、权限、原子替换和恢复，错误语义不完全一致。

## 2. 破坏性边界

- 删除整个通用 `/api/send`、令牌命令和主动发送回执；排空、恢复和部署提交只接受本机控制通道。
- 删除 `Handler` 中跨领域的 `sync.Map` 菜单状态；工作空间、Codex 线程、codex-link-clawbot 队列、偏好、交付和安全各自拥有类型化控制器。
- 删除“无法识别就按顺序试多个 handler”的隐式路由。每个自然语言意图只归属一个领域，冲突在启动测试中直接失败。
- 删除内存菜单作为唯一事实来源；数字选择必须引用持久菜单 revision，过期或重启后明确拒绝，不进入 Codex。
- 不引入 SQLite 兼容层或双写。现有 JSON 状态一次性迁入统一状态内核后，旧写入器全部删除。

## 3. 控制面结构

```text
微信消息
  └─ 入站信封
       ├─ 来源键 / 绑定者 / 上下文令牌 / 附件
       └─ 意图路由
            ├─ 项目控制器
            ├─ 线程控制器
            ├─ codex-link-clawbot 队列控制器
            ├─ 偏好控制器
            ├─ 交付控制器
            └─ 安全控制器
                    │
                    ▼
              类型化动作结果
              ├─ 卡片模型
              ├─ 短指令
              ├─ 队列请求
              └─ 投递请求
```

路由器只负责标准化文本、识别唯一意图和转交，不读取领域状态。控制器只返回类型化结果，不直接发送微信。最外层 Delivery Presenter 根据当前视觉风格统一渲染并投递。

每个动作声明：

- 稳定 action ID 与所属领域。
- 是否需要 `context_token`。
- 是否允许远程锁定、排空或轮次执行期间调用。
- 是否修改状态、是否需要二次确认。
- 幂等来源键与安全审计摘要。

## 4. 持久菜单 revision

每个绑定者最多保存一项当前交互：

```json
{
  "version": 13,
  "owners": {
    "owner": {
      "revision": "random-id",
      "view": "queue.detail",
	  "mode": 1,
	  "expires_at": 1786000000,
	  "options": [
		{"code": "1", "action": "queue_retry", "subject": "task-id"}
	  ],
	  "back": {"action": "queue_page"}
	}
	},
	"receipts": {}
}
```

正文、卡片图片、提示词、路径和 `context_token` 不进入菜单状态。用户回复数字时必须同时满足：当前绑定者、revision 未过期、目标仍属于该绑定者、动作仍适用于当前状态。服务重启后可以继续同一操作；过期数字只返回“操作已失效”，绝不交给 Codex。

所有改变状态的控制动作按微信来源键保存最小回执。长轮询重投时复用动作结果，不重复归档、删除、取消、锁定或触发请求复用。

## 5. 统一状态内核

新增单一 `statefile` 包，所有领域状态复用：

- 严格版本、未知字段和尾随数据拒绝。
- 文件 `0600`、目录 `0700`，拒绝符号链接和非普通文件。
- 同目录临时文件、`fsync`、原子改名和父目录同步。
- 进程内读写锁与跨进程独占锁；离线迁移和运行时不能同时写。
- 固定大小上限、备份清单、校验哈希和孤儿临时文件清理。
- 统一错误分类：schema、权限、容量、损坏、冲突、暂不可用。

迁移顺序按风险从低到高：偏好与工作空间选择 → 菜单与远程锁 → 交付与待阅通知 → Codex 线程索引。codex-link-clawbot 请求队列继续保留独立事务目录，但复用底层原子文件与锁实现。

## 6. API 权限模型

### 本机管理面

健康、排空、恢复和部署提交迁移到 Unix domain socket；CLI 固定连接该 socket，并校验 socket 所有者和 `0600` 权限。TCP 上不再暴露 `/admin/*`。

不存在通用主动发送面。部署事件和长任务恢复提醒只写入受限待阅状态；运行中服务仅在绑定者下一次携带有效微信上下文交互时合并补送。

## 7. 自诊断

“运行中心”新增一个真正有用的“为什么没回复”入口，也可以直接发送同名短语。它只读取确定性状态：

- 当前运行状态与 Codex 是否就绪。
- 微信监控是否健康、最后成功轮询距今多久、是否卡在待提交批次。
- 当前 Codex 轮次阶段、codex-link-clawbot 请求队列是否暂停或远程锁定。
- 本次运行最近一次持久化错误分类。
- 最近投递是成功、明确失败还是可能部分可见。

结果使用不依赖渲染器和持久菜单的高密度文字，最多展示三条依据和三个下一步操作，因此即使问题正是磁盘写入或卡片渲染也仍有机会返回。不得展示账号 ID、正文、路径、URL 查询参数、命令输出或环境变量。没有确定性阻断时必须明确说明“不能断言”，不得猜测原因。

## 8. 实现分层

### A. 状态内核

- 已完成 `statefile`、锁、错误分类、故障注入、清单和现有状态迁移器。
- 已迁偏好、工作空间选择、远程锁、Codex 线程、待阅通知、交付、微信游标与 codex-link-clawbot 请求队列 JSON；菜单直接建立 revision 状态，不保留旧内存双写。

### B. 类型化控制器

- 已完成 Intent Registry、Action Result 与 Presenter。
- 已按系统、工作空间、Codex 线程、codex-link-clawbot 队列、偏好、交付和安全拆分旧路由，删除旧大 switch 和跨领域 map。

### C. 持久交互

- 已完成菜单 revision、幂等控制回执、重启继续和严格过期。
- 所有二次确认均保存类型化 action，不保存显示正文、标签、路径、提示词或 `context_token`。

### D. 本机管理安全

- 已完成管理面 Unix socket 迁移：目录与 socket 分别强制 `0700`/`0600`，客户端逐次校验类型、所有者和权限，部署通知只能提交类型化版本元数据，由运行中服务生成固定正文并写入绑定者待阅状态。
- 已删除 TCP 健康与管理端点、整个主动发送面、发送令牌、发送回执、旧 `api_addr` 和直接读取微信凭据的 CLI 发送旁路。

### E. 诊断与真机验收

- 已完成“为什么没回复”、状态故障注入、重启数字回复和 Unix socket 越权自动化测试。
- 已修正微信业务错误响应的健康语义；登录过期或非零错误码不再刷新最近成功轮询。
- 真机验收必须覆盖菜单重启续接、锁定、队列控制和诊断文字。

## 9. 验收矩阵

1. 在 codex-link-clawbot 执行记录回复数字前重启服务，原操作仍可完成；过期 revision 明确拒绝且不启动 Codex。
2. 重投同一控制消息，请求复用、删除、取消和远程锁各只执行一次。
3. 任意两个意图注册同一规范化短语时测试失败，不能依赖注册顺序。
4. 任一状态写入在 write、sync、rename 或目录 sync 注入失败后，旧文件仍完整可读。
5. 运行时持锁时离线迁移拒绝启动；迁移持锁时服务拒绝启动。
6. TCP `/api/send` 与 `/admin/*` 均不存在；配置不接受发送面字段和命令。
7. Unix socket 非所有者不可连接，部署通知不能携带自由正文或收件人；提交成功必须返回 `deferred`，且待阅状态不得保存 `context_token`。
8. “为什么没回复”能分别识别队列暂停、远程锁、Codex 未就绪、微信监控异常、存储错误和投递歧义。
9. 所有卡片继续使用 Lucide 图标，不出现表情符号、内部路径、账号、令牌、原始输出或低信息量装饰。

## 10. 结果续接

成功纯文字请求在复用副本有效期内提供三种类型化动作：

- `task.continue_in_thread`
- `task.rerun`
- `task.continue_in_new_thread`

这些动作直接挂入成功执行详情，不引入独立模板、参数槽或额外持久状态。长期规范由项目 `AGENTS.md` 或 Codex Skill 承担。
