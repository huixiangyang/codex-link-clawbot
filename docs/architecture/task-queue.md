# codex-link-clawbot 持久请求队列与投递事务

## 1. 概念边界

codex-link-clawbot 必须区分两层概念：

- Codex 工作空间：受信任的本机目录选择。
- codex-link-clawbot 请求：已可靠接收、等待或完成交付的一条微信输入。
- Codex 线程：持续的上下文和历史。
- Codex 轮次：请求被协调器领取后，通过 `turn/start` 创建的一次执行。

`internal/request` 是 codex-link-clawbot 请求在 Codex 执行前后的可靠队列实现。`internal/execution` 拥有真实轮次阶段状态机，`internal/bridge` 只把它连接到微信发送。内部 `Task` 类型不改变用户概念：界面统一称为“请求”或“执行记录”，绝不称为 Codex 轮次。

## 2. 核心不变量

1. 文字、图片和文件在回复“已加入队列”前必须完整落盘。
2. 每个排队请求固定绑定创建时的绑定者、工作空间、目标 Codex 线程、回答方式与视觉风格。
3. 全部项目共用一个串行 Codex 执行协调器，不并发修改不同工作目录。
4. 重启后，未开始的请求继续排队；已中断的执行或发送不自动重试。
5. 发送前先冻结完整结果和交付物，避免在不确定状态下重复执行 Codex。
6. 运行阶段只接受当前 `turnId` 的结构化 App Server 事件；重复、跨轮次和终态后的迟到事件全部忽略。

## 3. codex-link-clawbot 请求状态机

```text
微信消息
  └─ staging ── 下载附件、校验并写入私有目录
       └─ queued ── 已持久化，可安全向微信确认
            └─ running ── 协调器独占 Codex 与固定项目
                 ├─ Codex turn/start ── 创建并执行 Codex 轮次
                 └─ delivering ── Codex 轮次已结束，结果已冻结并正在发送
                      ├─ succeeded
                      ├─ failed
                      └─ interrupted

queued ── 用户删除 ── cancelled
running ── 用户取消 ── cancelled
```

| 状态 | 重启处理 | 输入与结果 |
| --- | --- | --- |
| `queued` | 保持排队 | 保留完整请求与附件 |
| `running` | 改为 `interrupted` | 最多保留 24 小时，等待人工决定 |
| `delivering` | 改为 `interrupted` | 保留冻结结果，不重复执行 |
| `succeeded` | 保持 | 删除敏感负载，只留安全元数据 |
| `failed` / `interrupted` | 保持 | 最多保留 24 小时供显式重试 |
| `cancelled` | 保持 | 立即删除请求与临时结果 |

## 4. 持久化布局

```text
~/.codex-link-clawbot/tasks/
  index.json
  <record-id>/
    request.json
    inbox/
    result.json
    outbox/
```

- 目录固定为 `0700`，JSON、附件和结果固定为 `0600`。
- 全部相对路径禁止绝对路径、`..` 和符号链接。
- `request.json` 保存执行所需的完整输入、附件元数据、来源键和当前微信上下文令牌，进入终态后立即删除。
- `result.json` 只在发送、失败或中断阶段存在，用于在不重新执行 Codex 的前提下处理发送失败。
- 索引不存正文、附件名、绝对路径、回答正文、终端输出或凭据。
- 每个绑定者最多 20 个待执行请求和 20 条终态元数据；队列附件总量上限 500 MiB。

## 5. 原子入队

1. 微信监控取得一批消息，但暂不提交新游标。
2. 本机控制意图同步处理；普通输入进入暂存区。
3. 附件全部下载、校验并同步到私有目录。
4. 暂存目录原子改名，并将队列记录原子加入索引。
5. 只有上述步骤全部成功，才向微信确认已开始或已排队；确认发送完成前，协调器不得领取这条请求。
6. 整批消息均已消费或可靠入队后，才提交微信游标。

来源键优先使用微信账号与消息编号，缺失时使用账号与序号。同一来源键再次出现时返回既有记录，不重复下载附件或创建 Codex 轮次。

## 6. 执行协调

进程中只允许一个 codex-link-clawbot 请求处于执行或发送状态：

1. 从全局先进先出队列中领取最早的可执行记录。
2. 解析并固定受信任工作空间，把根目录显式传给线程创建、恢复和轮次请求；不存在共享工作目录切换。
3. 使用记录中固定的线程；为空时在该项目新建线程并回写。
4. 为本请求创建私有交付目录，启动 Codex 轮次并只更新安全阶段信息。开始、推理、计划、执行、生成最终回答和终态来自 `turn/started`、`item/started`、`turn/plan/updated` 与 `turn/completed`，不从说明文字或输出推断。
5. Codex 完成后先冻结发送计划，再按入队时的回答方式和视觉风格投递。
6. 得到确定结果后进入终态，清理敏感负载，然后领取下一项请求。

文件媒体只有在微信明确发送成功后才复制到严格 v3 交付箱。交付记录继承本请求冻结的工作空间和线程，并写入请求 ID、大小与 SHA-256；最近结果因此能和交付详情使用同一来源。再次发送不创建 Codex 轮次，只在摘要复核通过后发送私有副本；副本失效时明确拒绝，不回退为重新执行。

用户在排队后切换项目入口、Codex 线程、视觉风格或回答方式，不改变已有请求。固定项目入口或线程在执行前已不存在时，该请求直接失败，不猜测其他项目或线程。

阶段报告器以当前轮次 ID 为归属边界，并以阶段和计划快照生成签名。默认首条阶段消息等待 15 秒并合并期间变化，之后只发送不同签名；没有定时文字保活。完成、失败或中断事件会冻结报告器并取消待发送阶段，最终结果、失败说明或取消回执成为唯一终态。阶段微信发送失败只丢失中间提示，不能阻塞或取消 Codex 事件流。

## 7. 微信交互

所有队列操作进入“codex-link-clawbot 请求队列”：

- `31` 新建工作。
- `32` 在目标线程审查改动。
- `33` 查看请求状态与记录；暂停、继续和清空队列位于该页面。
- `34` 取消当前执行；如果 Codex 轮次已经启动，同时请求中断。

首页只显示当前状态、等待数量、暂停状态和最近结果。卡片不显示完整问题、附件名、原始账号、绝对路径或内部记录编号。

## 8. 验证

```bash
go test ./...
go test -race ./internal/statefile ./internal/request ./internal/bridge ./internal/ilink ./internal/management ./internal/cli
go vet ./...
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build ./cmd/codex-link-clawbot
CGO_ENABLED=0 GOOS=linux GOARCH=arm64 go build ./cmd/codex-link-clawbot
```

真机至少覆盖：Codex 长轮次执行期间连续排入文字、图片和 PDF；切换项目入口与线程后既有请求仍使用冻结快照；排队、执行和发送阶段重启；取消、暂停、继续、清空，以及发送结果不确定后在下一次有效交互中收到恢复提醒。
