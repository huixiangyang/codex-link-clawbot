# v2.5 持久任务队列与安全部署规格

## 1. 目标

`v2.5` 把微信消息处理从“收到后立即占用 Codex，忙碌时只在内存暂存一条文字”重构为“先可靠入队，再由单一执行协调器消费”。这一版本只解决任务不丢、项目不串、附件可排队、重启可解释和升级可回滚，不引入并发 Codex、自由 Shell 自动化或永久回答记忆。

必须同时满足：

1. 普通文字、图片和文件在回复“已加入队列”前已经完整落盘。
2. 每项任务固定绑定创建时的绑定者、项目、会话、回答方式与视觉风格。
3. 全部项目共用一个串行 Codex 执行协调器，`cwd` 只在协调器持有执行权时切换。
4. 重启后未开始任务继续排队；中断的执行与发送绝不自动重试。
5. 升级先排空正在执行和发送的任务，再替换二进制；失败时恢复二进制、配置与状态快照。

## 2. 破坏性边界

- 删除 `pendingInstructions`、`queuePendingInstruction`、`drainPendingInstruction` 与“清除暂存”语义。
- 删除按绑定者并发的 `activeTasks`；改为进程内唯一 `Coordinator` 和持久任务状态。
- 删除内存五分钟消息去重作为任务可靠性依据；队列任务使用微信消息来源键幂等创建。
- 删除 `task-history.json` 与独立 `ActivityStore`；实时队列和最近任务统一来自新的任务索引。
- 删除 `update`、`upgrade`、不受控 daemon 重启与生产机 `cutover-local.sh`；升级只使用事务式 `weclaw deploy`，普通 `restart` 改为排空后的 systemd 重启。
- 不读取或自动迁移旧任务记录。旧文件只在部署快照中保留，运行时不会兼容。

会话、项目、偏好、素材与交付状态继续使用现有严格 schema；本版本不顺带合并无关状态文件。

## 3. 任务状态机

```text
微信消息
  └─ staging ── 下载并校验附件、写入私有请求目录
       └─ queued ── 已持久化，可安全确认给微信
            └─ running ── 协调器独占 Codex 与项目 cwd
                 └─ delivering ── 结果及交付物已冻结，正在发送
                      ├─ succeeded
                      ├─ failed
                      └─ interrupted

queued ── 用户删除 ── cancelled
running ── 用户取消 ── cancelled
```

状态含义：

| 状态 | 是否自动执行 | 重启处理 | 输入/结果保留 |
| --- | --- | --- | --- |
| `queued` | 是 | 保持排队 | 保留完整请求与附件 |
| `running` | 已执行 | 改为 `interrupted` | 保留请求，等待人工决定 |
| `delivering` | 已执行 | 改为 `interrupted` | 保留冻结结果，避免重复执行 |
| `succeeded` | 否 | 保持 | 立即删除请求与临时结果，只留元数据 |
| `failed` | 否 | 保持 | 最多保留 24 小时供人工重试 |
| `interrupted` | 否 | 保持 | 最多保留 24 小时，不自动重试 |
| `cancelled` | 否 | 保持 | 立即删除请求与临时结果，只留元数据 |

执行中断可能已经修改工作区，发送中断可能已经让部分媒体可见，因此“重试”必须由用户显式触发。重试创建一个新的任务 ID，并在元数据中记录来源任务；原记录不回退状态。

## 4. 持久化布局

```text
~/.weclaw/tasks/
  index.json
  <task-id>/
    request.json
    inbox/
      image-01.png
      file-01-report.pdf
    result.json
    outbox/
```

- `tasks/` 与每个任务目录固定 `0700`，JSON、附件和结果固定 `0600`。
- `index.json` 使用严格 v1 JSON、未知字段拒绝启动、私有临时文件同步后原子替换。
- 所有任务内路径均为相对路径；schema 禁止绝对路径、`..` 和符号链接。
- `request.json` 保存执行所需的完整用户输入、附件元数据、来源消息键和当前 `context_token`。令牌不进入索引、日志、卡片或历史，任务终态后立即删除。
- `result.json` 只在 `delivering`、`failed` 或 `interrupted` 阶段存在，用于在不重复执行 Codex 的前提下处理发送失败；成功发送后立即删除。
- 索引最多保留每个绑定者 20 条终态元数据、20 条待执行任务；单任务沿用 100 MiB 附件上限，全部队列附件总量上限 500 MiB。
- 启动时清理没有索引记录的 staging/任务目录，并删除超过 24 小时的失败或中断负载；对应元数据保留，但不再提供重试。

索引中的任务元数据至少包含：

```json
{
  "id": "task-id",
  "source_message_key": "account:message-or-seq",
  "owner_id": "bound-owner",
  "project_id": "weclaw",
  "thread_id": "optional-codex-thread",
  "summary": "脱敏摘要",
  "state": "queued",
  "stage": "等待执行",
  "response_mode": "adaptive",
  "visual_style": "editorial",
  "created_at": 1785916800,
  "started_at": 0,
  "finished_at": 0,
  "retry_of": "",
  "input_tokens": 0,
  "output_tokens": 0,
  "total_tokens": 0
}
```

完整正文、附件名、绝对路径、回答正文、终端输出和凭据不得进入 `index.json`。

## 5. 原子入队与微信同步

当前监控器在启动消息处理协程前就保存同步游标，进程退出时无法证明消息已经进入任务状态。新链路按以下顺序执行：

1. `GetUpdates` 取得一批消息，但暂不保存新的同步游标。
2. 控制意图在本机同步处理；普通输入进入任务 staging。
3. 附件全部下载、校验并写入 `.staging-<task-id>`，随后写入并同步 `request.json`。
4. staging 目录原子改名为正式任务目录，任务元数据原子加入 `index.json`。
5. 只有上述步骤成功，才向用户确认“已开始”或“已加入队列”。
6. 一批消息均已消费或可靠入队后，监控器才原子保存新的同步游标。

来源键优先使用 `account_id + message_id`；`message_id` 缺失时使用 `account_id + seq`。同一来源键再次出现时返回已有任务，不重复下载附件或创建 Codex turn。校验失败属于已消费消息，向微信发送明确错误后允许推进游标；持久化和磁盘错误属于可重试错误，不推进游标。

监控器不再为每条消息创建无跟踪 goroutine。入站处理只负责控制路由和可靠入队，Codex 执行完全离开长轮询路径。

## 6. 执行协调器

进程只允许一个任务处于 `running` 或 `delivering`：

1. 从全局 FIFO 中领取最早的、绑定者未暂停且未远程锁定的 `queued` 任务。
2. 按任务记录解析受信任项目，独占设置 Codex `cwd`。
3. 使用任务固定的 `thread_id`；为空时在固定项目中新建会话并回写任务元数据。
4. 创建 turn 私有 outbox，运行 Codex，持续更新索引中的安全阶段说明和 token 用量。
5. Codex 完成后先冻结完整发送计划到 `result.json`，再把状态改为 `delivering`。
6. 按任务快照的回答方式与视觉风格发送；得到确定结果后进入终态并清理敏感负载。
7. 领取下一项任务。

用户在任务排队后切换项目、会话、视觉风格或回答方式，不改变已有任务。项目或会话在执行前已不存在时，任务进入 `failed`，不得偷偷改到当前项目或新会话。

远程锁定会取消当前任务并暂停该绑定者队列，但保留已落盘任务。解锁后仍需用户明确“继续队列”，避免一解锁就恢复执行旧操作。

## 7. 微信交互

不新增命令墙，所有管理动作进入“任务中心”：

- 空闲主菜单：项目、会话、任务中心、更多功能。
- 执行中主菜单：当前任务、任务中心、当前会话、更多功能。
- 普通消息在空闲时入队并立即执行；忙碌时入队并返回位置、项目和安全摘要。
- 图片和文件与文字完全同等排队，不再要求任务结束后重发。
- 直接说“任务队列”“排队任务”“暂停队列”“继续队列”可进入对应本机控制链。

任务中心首页只显示当前状态、等待数量、暂停状态和最近结果，分页每页 6 项。详情按状态提供最少动作：

| 任务状态 | 可用动作 |
| --- | --- |
| 排队 | 移到最前、删除任务 |
| 执行 | 刷新状态、取消任务 |
| 发送 | 刷新状态 |
| 失败/中断 | 重试、删除任务 |
| 完成 | 查看交付、再次发送 |

“清空队列”必须二次确认，只删除当前绑定者的排队任务，不影响执行中任务和其他绑定者。队列卡不显示完整问题、附件名、原始账号 ID、绝对路径或内部任务 ID，只显示短编号和脱敏摘要。

“移到最前”只调整等待区顺序，不抢占正在执行或发送的任务。一个绑定者暂停队列时不阻塞其他绑定者已经排队的任务；全局协调器仍按可执行任务的 FIFO 顺序领取。

## 8. 排空与健康协议

运行状态统一为 `starting`、`ready`、`draining`、`stopping`、`degraded`。`GET /health` 返回不含隐私信息的 JSON：

```json
{
  "status": "ready",
  "version": "v2.5.0-queue.1",
  "uptime_seconds": 3600,
  "codex": {"ready": true},
  "wechat": {"monitors": 1, "healthy": 1},
  "tasks": {"running": 1, "queued": 3, "delivering": 0},
  "draining": false
}
```

排空期间继续接收并持久化微信任务，但协调器不领取新任务；控制菜单仍然可用。排空完成条件是：没有 `running`、没有 `delivering`、没有正在提交的 staging，并且同步游标已经覆盖所有成功入队的消息。

只有回环地址可以调用管理端点。`POST /admin/drain` 进入排空，`POST /admin/resume` 在部署取消时恢复；非回环 API 认证统一放在 `v2.6`，本版本继续拒绝非回环管理调用。

`/health` 始终返回上述 JSON；`ready` 与 `draining` 使用 HTTP 200，`starting`、`degraded` 与 `stopping` 使用 HTTP 503。部署流程根据 JSON 字段判断排空完成，不能只把端口可连接当作就绪。

## 9. 事务部署

`weclaw deploy <version>` 从发布页部署不可变版本；本地开发构建使用 `weclaw deploy --binary /absolute/path --expect-version <version>`，两条路径进入完全相同的事务流程。微信控制层不开放部署入口。

部署步骤：

1. 下载目标二进制与校验清单，验证 SHA-256、平台和目标版本。
2. 请求旧进程排空并轮询结构化健康状态；默认最多等待 10 分钟，不强杀活动任务。
3. 在私有备份目录保存旧二进制、配置和全部状态文件清单。
4. 以同目录临时文件、同步和原子改名安装新二进制。
5. 通过 systemd 用户服务重启，等待目标版本进入 `ready`。
6. 主动发送纯文字就绪通知并记录部署收据。
7. 新版本未就绪时停止服务，恢复完整快照与旧二进制，再次启动并验证旧版本健康。

部署命令要求显式的 systemd 用户服务名或使用固定默认值，不依赖调用者 PATH、当前目录、PID 猜测、后台 daemon 或生产机专用脚本。事务快照目录固定 `0700`、内容固定 `0600`；包含排队正文、附件或令牌的快照在成功切换 24 小时后删除，长期只保留二进制、配置和无正文部署收据。

状态 schema 不做运行时兼容；需要新 schema 的版本在旧进程停机后调用目标二进制的一次性离线迁移命令，迁移失败立即回滚完整快照。普通 `weclaw restart` 复用排空与健康检查，但不替换二进制或执行迁移。

## 10. 开发批次

### A. 状态底座

- 新建严格 v1 任务索引、私有任务目录、原子 staging 和崩溃清理。
- 用新任务索引替换 `ActivityStore`，删除旧暂存与任务历史实现。
- 验证权限、容量、相对路径和消息来源键幂等。

### B. 入站与执行分离

- 把监控器改为“处理成功后推进游标”。
- 普通消息只负责可靠入队；新增单一 `Coordinator` 消费 FIFO。
- 项目和会话全部改为显式任务快照，不再从执行时 UI 当前值推断。

### C. 微信任务中心

- 完成列表、详情、分页、移到最前、删除、暂停、继续、取消和重试。
- 重构主菜单和自然语言控制，图片与文件忙碌时直接排队。
- 远程锁定与队列暂停形成一致状态。

### D. 交付事务

- `sendReplyWithMedia` 返回结构化发送收据，不再只写日志。
- 冻结 `result.json`，区分未开始发送、明确失败、可能部分可见和完整成功。
- 对发送中断执行人工恢复流程，禁止自动重复 Codex turn 或整批正文。

### E. 排空与部署

- 实现运行状态控制器、结构化健康接口和排空管理端点。
- 删除旧更新、不受控 daemon 重启和本机切换路径，完成安全 `restart`、`weclaw deploy` 与自动回滚。
- 完成 systemd、异常退出和真实微信升级验收。

每个批次独立提交并通过全仓测试，但只有 A–E 全部通过后才部署 `v2.5`。

## 11. 验收矩阵

1. 启动一个长任务，连续发送两条文字、一张图片和一个 PDF；四项均只入队一次并按顺序执行。
2. 排队后切换项目、会话和回答方式；已有任务仍使用创建时快照，新任务使用新选择。
3. 在 `queued`、`running` 和 `delivering` 三个阶段分别终止进程；重启后的状态必须符合状态机，禁止静默自动重试中断项。
4. CDN 预上传失败、首项明确拒绝、发送响应丢失和部分媒体可见时，任务状态与重试入口必须不同。
5. 重复投递同一微信 `message_id` 或 `seq`，不得产生第二个任务或再次下载附件。
6. staging 写盘失败时不得推进微信同步游标；恢复磁盘后同一消息可以成功入队。
7. 远程锁定必须取消当前任务、暂停队列并阻止领取；解锁后不自动恢复。
8. 排空期间新消息可以可靠入队但不能开始；取消排空后按原顺序继续。
9. 新版本启动失败时必须恢复旧二进制、旧配置、旧状态和旧健康版本。
10. 真机确认任务中心卡片、分页、取消、图片/文件排队、重启恢复和部署通知均可见，且没有账号 ID、路径、令牌、原始 diff 或终端输出泄露。

验证命令至少包含：

```bash
go test ./...
go test -race ./taskqueue ./messaging ./ilink ./api ./cmd
go vet ./...
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build ./...
CGO_ENABLED=0 GOOS=linux GOARCH=arm64 go build ./...
```
