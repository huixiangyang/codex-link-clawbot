# 产品与业务体系复核

状态：重构前的审计记录。用户已确认调整方向，实施已按[业务设计](../../specs/business-reset/design.md)完成本地验证；当前行为以[工作台指南](../guides/workbench.md)为准。下文保留原始问题证据，不作为当前能力说明。

## 判断

当前系统具备可靠传输与执行的一部分基础，但用户侧缺少完整的“选定上下文 → 发起请求 → 跟踪执行 → 获取结果 → 处理异常 → 继续对话”闭环。上一轮调度与生命周期重构改善了工程边界，没有解决这些业务缺口。

“管理台有页面”“底层有方法”“用户可以完成操作”是三个不同的成熟度。下面按实际生产调用链核对，不将测试覆盖或未接入的方法计为产品能力。

## 已有能力与缺口

| 用户场景 | 当前实际实现 | 业务影响 | 调整建议 |
| --- | --- | --- | --- |
| 首次发送后继续追问 | 自动创建线程时登记为非活动目标；入队继续读取活动目标引用 | 未手动选线程时，按代码路径会为后续请求继续新建线程，缺少默认对话连续性 | 每个绑定与工作空间拥有明确的当前会话；首次消息建立会话，后续消息沿用 |
| 确认消息将发往哪里 | 目标信息来自最近 12 个线程的列表扫描 | 当前目标不在第一页时，被显示为未选择或自动创建 | 独立解析当前目标，列表分页不能决定目标是否存在 |
| 切换工作空间与线程 | 先保存工作空间，再尝试选择或新建线程 | 线程操作失败，工作空间却已切换；下一条微信消息可能进入意外目录 | 切换目标是一次完整业务操作；失败不改变原目标 |
| 查看所有待处理请求 | 前端只显示请求数组前 6 项，没有分页或详情 | 用户看不到被截断的等待项，也无法查完整输入、错误和结果 | 请求中心区分进行中、待处理、历史，并可查详情与分页 |
| 判断任务到底有没有完成 | 一个任务终态同时表示 Codex 执行和微信发送结果 | Codex 已完成但发送失败，被呈现为任务失败或中断 | 分别呈现执行结果与投递状态，恢复动作据此选择 |
| 取回已经成功的回答 | 成功后清理完整请求目录；只为成功纯文字请求保留复用提示词 | 网页无法提供成功结果详情；微信之外没有统一的结果记录 | 结果成为独立留存对象，输入清理不删除仍在保留期的结果 |
| 执行失败后恢复 | 底层实现 `Retry`，生产入口没有调用 | 用户看到失败，却无法通过管理台完成恢复 | 明确区分重新执行与重新投递，记录原请求关联 |
| 文件发送失败后取回 | 文件仅在微信发送成功后尝试归档；失败副本留在临时请求目录 | 最需要取回的失败文件反而不在交付列表中 | 先归档结果和产物，再进行渠道投递；下载独立于微信发送 |
| 从交付列表拿到文件 | 展示名称、大小和可用状态，没有下载入口 | “可交付”只是状态文字，不能完成取回 | 支持认证下载，并展示来源请求、线程和留存时间 |
| 管理多个绑定 | 服务加载所有凭据，控制台固定使用 `accounts[0]` | 账号数量与可管理范围不一致，其他账号缺少同等控制入口 | 必须明确选择单绑定产品，或完整实现绑定选择与隔离 |
| 选择语音/阅读能力 | 返回全部模式选项，未按当前语音与视觉配置过滤 | 可以选中本实例无法履约的模式 | 按实例真实能力显示、验证与保存设置 |
| 修改偏好 | 先保存模式，再保存风格 | 第二步失败时出现部分保存；页面提示失败但状态已改变 | 一次提交整体校验和保存；后台刷新不覆盖未保存表单 |
| 维护线程 | 底层有改名、归档、分支、目标等大量方法；界面只接入新建和选择 | 能力边界与维护成本不匹配 | 先完成必要的会话管理；高级能力按明确场景取舍 |

以上是静态代码与生产调用点复核，未对真实微信账号或 Codex 实例进行操作。对自动线程行为的判断来自调用链推导，不是已执行的实机复现。

## 推荐产品主线

建议将产品定义为“个人 Codex 远程工作台”：微信负责低成本发起和继续工作，Web 负责定位上下文、查看完整结果和处理异常，CLI 负责本机安装与运维。这是推荐方向，尚待用户确认，不将现有 README 的定位自动当成最终需求。

核心业务对象收敛为：

| 对象 | 业务含义 |
| --- | --- |
| 绑定 | 谁通过哪个微信连接使用当前实例，是远程工作状态的归属边界 |
| 工作空间 | 被允许执行任务的目录范围，不等同于任务或线程 |
| 当前会话 | 某个绑定在某个工作空间继续交流的 Codex 线程 |
| 请求 | 用户的一次完整意图，包含入队时确定的上下文与输入 |
| 执行记录 | 请求是否开始、如何结束及产生了什么结果 |
| 结果 | 已生成的回答与产物，不依赖微信是否发送成功 |
| 投递记录 | 向微信发送结果的尝试与回执，不能改变既有执行事实 |

用户默认看到“正在处理什么、需要处理什么、已经产出了什么”。工作空间与线程是上下文选择，运行指标是运维信息，不应与请求和结果争夺主入口。

## 功能取舍

### 必须形成闭环

1. 首次启动可解释当前可用性；账号、工作空间、Codex 和可选输出能力各自有明确状态。
2. 默认会话连续，手动切换只影响新请求；入队确认明确上下文。
3. 请求详情能查看状态、失败原因、结果和产物，并给出当前可执行的操作。
4. 完成结果可取回，微信失败不丢失产物、不要求重新运行 Codex。
5. 重跑、取消、队列暂停、排空、锁定分别有清楚且一致的语义。

### 保留但降低优先级

阅读图、语音、视觉风格属于输出方式。应由可用能力约束，待文字与文件结果闭环完成后再完善，不作为核心任务能否完成的依赖。

### 暂不扩展

团队协作、审批流、周期调度、并行任务农场、完整复制 Codex 的高级线程控制。没有用户场景支撑的旧入口、模板和业务方法，在实现阶段按调用审计决定删除，不因“底层已经写过”而补一排按钮。
