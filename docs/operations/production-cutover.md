# 首次生产切换与真机验收

更新日期：2026-08-06

本文只描述 `v2.5.0-queue.1 → 当前 v2.7 主线` 的首次生产切换。它不是日常部署教程。完成这次跨管理面切换后，后续版本统一使用 `weclaw deploy`，不为 v2.5 保留兼容客户端或服务器。

## 1. 已知基线

| 项目 | 当前事实 |
| --- | --- |
| 生产版本 | `v2.5.0-queue.1`，Linux amd64 |
| 服务状态 | systemd 用户服务运行中，Codex 就绪，微信监控健康 |
| 旧管理面 | 回环 TCP，单元仍包含 `start --api-addr 127.0.0.1:18011` |
| 主线能力 | v2.6 Unix 管理面、统一状态内核与控制器；v2.7 持久工作流与结果续接 |
| 首次切换限制 | 新 CLI 只理解 Unix socket，不能排空仍运行的 v2.5 TCP 服务 |

2026-08-06 已完成一次不接触生产运行时的预演：

- 复制完整生产状态到独立临时目录。
- 使用主线候选持有独占迁移锁并完成离线迁移。
- 确认 `api_addr` 删除且 `send_api.enabled=false`。
- 确认一个项目中的三个旧快捷任务迁入一个绑定者的严格 v1 `workflows.json`，配置不再含 `quick_tasks`。
- 使用 v2.7 配置解码器对迁移后的真实配置完成严格解析和完整校验；一个项目、一个自动化、视觉和语音均有效。

这只证明迁移与配置可行，不替代候选启动、真实微信和回滚验收。

## 2. 角色与停止条件

维护窗口必须有一名执行者和一名验收者；只有执行者可以修改二进制、状态和 systemd 单元。开始前约定最长停机时间与无条件回滚时刻。

出现下列任一情况立即停止前进并回滚：

- 候选版本、架构或 SHA-256 与发布记录不一致。
- 旧服务无法完成排空，或排空前仍有运行、发送、暂存、待提交同步批次。
- 任一备份缺失、清单校验失败或备份路径与生产路径混淆。
- 离线迁移失败、输出未知 schema，或迁移后配置/工作流/账号无法严格读取。
- 候选的 Codex、微信监控、Unix socket、任务计数或版本不符合基线。
- 真实微信出现确认后丢失、重复执行、跨项目/绑定者越权或多媒体部分发送。
- 达到约定回滚时刻仍未完成最小验收。

## 3. 窗口前冻结

- [ ] 冻结 `main`；切换期间不合并 P5 或任何新状态 schema。
- [ ] 选择不可变候选版本，例如 `v2.7.0-rc.1`，二进制内版本与文件名一致。
- [ ] 执行 `go test -race ./...`、`go vet ./...` 和 Linux amd64/arm64 构建。
- [ ] 记录候选 Git commit、版本 JSON、SHA-256、构建时间和执行者。
- [ ] 再做一次最新生产状态副本的离线迁移；不得在副本上启动微信轮询。
- [ ] 对迁移后的配置执行严格校验，对备份与迁移结果执行私有清单校验。
- [ ] 验证旧二进制仍能独立输出 `v2.5.0-queue.1`，并准备离线可恢复副本。
- [ ] 记录切换前健康：版本、Codex、微信监控数、运行/等待/发送任务数与排空状态。
- [ ] 选择一条不会产生业务副作用的测试消息和一个可安全使用的测试项目。

候选不得直接覆盖唯一的旧二进制副本；状态备份不得放在 `~/.weclaw` 内，也不得被候选启动过程访问。

## 4. 首次切换顺序

严格按以下顺序执行，不合并步骤：

1. 使用当前已安装的 v2.5 二进制执行 `weclaw stop`。这个命令通过旧 TCP 管理面请求排空，确认完成后再停止 systemd 服务。
2. 再次确认服务为 `inactive`、旧 TCP 已关闭、没有运行中的 WeClaw 进程，并确认状态独占锁可以由离线进程获取。
3. 分别备份旧二进制、systemd 单元和完整状态根；生成包含路径、大小和 SHA-256 的只读清单。
4. 把候选安装到固定二进制路径，但保留可独立恢复的旧二进制副本。
5. 运行候选的 `migrate-state --root <state-root>`；迁移只允许执行一次，重复执行仅用于验证幂等，不作为失败修复手段。
6. 将 systemd 单元改为唯一的 `ExecStart=<candidate> start --draining`，删除 `--api-addr` 与其他已废弃参数，然后 `daemon-reload`。
7. 启动候选，使用候选 `weclaw status` 通过 `~/.weclaw/control.sock` 读取结构化健康。
8. 在排空状态核对精确版本、Codex 就绪、全部微信监控健康、队列数量、同步状态、项目、偏好、会话与三个迁移工作流。
9. 将单元改回唯一的 `ExecStart=<candidate> start`，移除 `--draining` 后重启服务。
10. 等待状态进入 `ready` 且 `draining=false`，再开始真实微信最小验收。

启动候选前禁止使用旧 TCP `/health` 作为成功证据；它必须消失。候选成功证据只能来自权限为 `0600`、所有者正确的 Unix socket 和真实微信。

## 5. 真实微信最小验收

### 5.1 控制面与状态

- [ ] 发送 `/`，主菜单最多四项，当前项目、任务和推荐入口符合当前状态。
- [ ] 打开菜单后重启服务，原数字选项仍可执行；过期数字明确失效且不进入 Codex。
- [ ] 验证项目切换；旧项目会话与工作流不能出现在新项目。
- [ ] 完成会话新建、搜索、切换、重命名、归档和恢复。
- [ ] 打开运行中心，验证状态、队列、远程锁定/解锁和“为什么没回复”。

### 5.2 任务与输入

- [ ] 连续发送文字、图片和 PDF，三项只入队一次并按固定上下文执行。
- [ ] 排队后切换项目、会话、回答方式和风格；旧任务仍使用创建时快照。
- [ ] 验证等待项移到最前、暂停、继续、删除；运行项验证取消与重试。
- [ ] 在等待任务存在时重启服务，队列与附件仍可恢复，执行中任务不被盲目重放。
- [ ] 同一微信来源重投不得创建第二个任务或第二次下载附件。

### 5.3 回答与交付

- [ ] 自适应模式的短回复使用文字，长回复使用当前视觉风格阅读卡。
- [ ] 阅读模式始终优先阅读卡，“文字版”可以取回完整正文。
- [ ] 语音模式先完成阅读图片和 MP3 的同批预上传，再按图片、音频顺序发送。
- [ ] 构造超长回答，确认完整阅读卡先送达，语音节选有明确说明且没有静默截断。
- [ ] 验证一个生成文件进入交付记录，任务临时目录清理后仍可再次发送。
- [ ] 分别切换刊物、构筑、黑标、可爱、简洁风格；不得出现表情符号、私有路径、账号、令牌、原始 diff 或终端输出。

### 5.4 持久工作流

- [ ] 三个旧快捷任务在对应项目中可见，数量与迁移前一致。
- [ ] 微信内新建一个包含两个 `「参数名」` 的工作流，逐项填写并只入队一次。
- [ ] 填写第一个参数后重启服务，第二个参数仍能继续；图片或文件不能误作参数。
- [ ] 完成重命名、编辑和二次确认删除；另一个项目不能访问当前工作流。
- [ ] 从成功纯文字任务执行继续原会话、原会话重跑、在新会话重跑和保存为工作流。
- [ ] 附件任务和过期任务不显示不可实现的保存或复用入口。

## 6. 回滚演练

首次切换不能只验证成功路径。候选完成排空启动验证后、恢复正常领取前，应在可控窗口注入一次不改变业务数据的启动失败，验证以下完整回滚：

1. 停止候选，确认不再持有状态锁。
2. 同时恢复旧二进制、原 systemd 单元和完整旧状态；不得只恢复二进制。
3. 校验备份清单后 `daemon-reload` 并启动旧服务。
4. 使用旧 v2.5 二进制通过旧 TCP 状态接口确认精确旧版本、Codex 和微信监控恢复。
5. 再按正式顺序重新执行候选迁移与启动；不能复用已被候选写入过的状态目录。

若维护窗口不允许在生产注入失败，至少要在同机隔离状态和独立 systemd 测试单元完成等价演练；此时 v2.7 仍标记为“有条件通过”，直到下一次真实故障或专门窗口补齐生产回滚证据。

## 7. 稳定观察与关闭

切换后观察 24–48 小时，期间不开发或部署 P5。关闭 G0 必须同时具备：

- [ ] 结构化健康持续为 `ready`，微信监控没有长时间不健康或待提交批次。
- [ ] 没有未知 schema、状态锁、权限、原子写入、投递歧义或队列重复错误。
- [ ] 任务结果、失败负载、控制回执和复用副本按各自时限清理。
- [ ] 主动发送 API 保持关闭，除非另有带 token 与最小 scope 的独立验收。
- [ ] 自动化现有计划只按指纹发送一次，不因迁移重复通知。
- [ ] 候选 commit、二进制 SHA、迁移清单、真机结果、回滚结果和最终版本被记录。

全部通过后才创建正式 v2.7 发布标记，并把生产状态从“待首次破坏性切换”改为“v2.7 基线已建立”。
