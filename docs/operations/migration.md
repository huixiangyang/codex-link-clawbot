# 离线迁移

当前业务模型只接受 `tasks/index.json` v4、`request.json` v2、`result.json` v2 和新的 `targets.json`。运行时不兼容旧格式，不根据旧文件猜测路由。

## 从上一版管理台升级

先停止旧服务，使用新二进制执行迁移。`--default-workspace` 必须填写配置中第一个工作空间的 ID；下面的 `workspace` 仅是默认配置的示例。

```bash
codex-link-clawbot stop
codex-link-clawbot migrate-business \
  --root "$HOME/.codex-link-clawbot" \
  --default-workspace workspace
codex-link-clawbot binding list
# 只有多个绑定或需要切换绑定时才选择：
codex-link-clawbot binding select <bot-id>
codex-link-clawbot start
```

迁移命令必须取得独占状态租约，运行中的服务会阻止迁移。它不连接微信、不启动 Codex，也不重新执行任何请求。

迁移流程：

1. 对请求、旧路由、会话索引和交付库生成大小/SHA-256 清单，拒绝符号链接与特殊文件。
2. 在状态目录建立 `.business-backup-<uuid>` 私有备份，再生成独立暂存副本。备份上限 4 GiB。
3. 将旧工作空间选择和线程引用导入持久化会话意图。v1 导入旧路由，v2/v3 保留现有目标。旧等待指令全部标记为“已取消，未执行”，移除暂停与确认等待字段、停用队列排序操作，不会自动执行。
4. 将尚存的旧回答、产物和投递回执转换为独立结果。执行中的请求记为中断；已有冻结结果的请求记为执行完成，未确认投递记为待确认。
5. 校验旧 `library.json` v3 的私有文件，将没有对应结果文件的历史交付导入独立请求记录，保留原请求编号与交付时间，导入结果保留 7 天。
6. 完整校验输入和结果，再发布 `tasks` 与 `targets.json`。未完成发布由迁移标记阻止启动；再次执行同一迁移命令会先恢复已校验备份，再重新转换。

成功后再次执行不会重复导入。缺失、损坏或超过容量的旧文件会使迁移失败；原状态保留，错误与备份路径会输出到终端。已经被旧版删除的回答无法恢复，只能迁移仍存在的文件与记录。

原 `library.json`、`deliveries` 与备份不会被当作新结果来源，也不会被新保留服务清理。确认新工作台可以取回结果后，可自行离线归档这些旧副本；保留备份会额外占用磁盘。

## 更早版本与自动部署

配置继续使用 schema 7。离线 `migrate-state` 将 schema 6 单向升级到 7，补充 `management.listen = 127.0.0.1:18120`，删除已经退役的微信数字控制状态，再调用同一业务迁移。受控部署流程会在停服、生成部署快照后执行该命令；失败按已有部署流程回滚。

更早的交付库 v1/v2 沿用历史迁移策略，不能可靠补齐请求、线程和摘要来源。升级前应单独归档旧交付文件。`migrate-business` 接受请求索引 v1/v2/v3；v1 同时导入交付库 v3，v2/v3 不重复导入旧文件库，遇到其他版本直接拒绝。

多个凭据不再全部启用。必须选择唯一绑定；未选中绑定的记录保留在私有状态中，不执行、不显示于当前工作台。切换绑定需停服后执行 `binding select`，然后启动。

迁移同时升级私有输入清单，保留 v3 的拒绝回执与结果投递历史。完成后删除运行目录中的 `project-state.json`、`session-index.json`、`library.json` 和 `deliveries/`；它们保留在校验备份内。启动只打开新状态，没有旧文件兼容分支。
