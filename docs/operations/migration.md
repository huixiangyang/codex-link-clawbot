# 离线迁移

`migrate-state` 仅用于将本项目最后一代 JSON 状态一次性导入 SQLite，不是服务启动时自动执行的兼容层。已经使用 SQLite 的实例不需要手工重复迁移；空的新实例直接配置启动。

## 支持范围

导入器接受配置 schema 7、请求索引 v4、输入与结果清单 v2，以及对应凭据、游标、绑定、目标、偏好、锁定、草稿、菜单回执和通知。更早版本必须先用匹配的旧程序完成旧业务升级，不能靠修改版本字段绕过校验。

运行时发现旧状态或未完成导入标记会拒绝启动。不要删除这些文件来“修复”启动，也不要让旧程序打开新的 SQLite 状态。迁移不连接微信、不启动 Codex、不执行工作或重发结果。

## 操作步骤

1. 保存当前程序版本和配置来源，确认备份空间与状态目录权限。
2. 停止当前实例，确保旧进程与服务管理器不会自动拉起；Linux 用户服务可先用旧程序的 `stop` 排空停服。
3. 使用已验证的新候选程序执行迁移，`--root` 必须显式指定规范绝对路径。
4. 校验配置、绑定和产物，再以新版本启动并按验收清单检查。

假设新候选位于 `/absolute/path/to/candidate`，默认状态根为：

```bash
/absolute/path/to/candidate migrate-state --root "$HOME/.codex-link-clawbot"
/absolute/path/to/candidate config
/absolute/path/to/candidate binding list
/absolute/path/to/candidate artifacts verify
```

后三条命令默认读取当前账号的状态根；迁移自定义根时，产物校验可加 `--root`，不要把默认根查询结果误认为自定义实例已通过检查。常规线上升级使用[事务部署](deployment.md#事务升级)，它会在停服并快照后调用同一导入器，无需提前手工迁移。

## 导入过程

导入器取得独占状态锁，枚举受管旧文件并检查版本、类型与完整性，拒绝符号链接、特殊文件和损坏附件，备份总量上限 2 GiB。

在 `.sqlite-import/` 构建数据库和产物目录，原数据仍保持不变；将原始文件复制到 `backups/json-<uuid>/original/` 并校验，随后检查暂存库完整性与外键。一致的 `data/` 目录通过一次重命名发布，再清理已经验证备份的旧运行文件、写入完成标记。

导入清单与完成标记存于 SQLite，不生成新的 JSON 状态。结果保留原时间，不因迁移延长有效期。未完成执行按重启规则处理，已完成事实保留；已被旧版本删除的正文和文件无法恢复。实现见 [sqlite.go](../../internal/app/migration/sqlite.go)。

## 失败与恢复

| 情况 | 处理 |
| --- | --- |
| 发布前失败 | 原始数据未改写；根据报错修复版本、权限、空间或损坏来源后重试 |
| 发布后、收尾前中断 | 启动保持拒绝；重跑同一迁移命令，验证备份后继续清理和提交 |
| 已成功导入 | 重复命令不重新导入，不延长结果期限 |
| 备份或旧来源在导入后被改动 | 停止重试并核对数据，不跳过清单校验 |

离线 JSON 备份不会自动过期，在确认新版本和业务数据正确前不要删除。回退需要停服，按备份清单恢复旧状态并使用对应旧程序；不要把旧文件与新 `data/` 混放，也不能覆盖升级后已经接收的新工作。事务部署的提交后不确定状态必须遵守[提交与回滚边界](deployment.md#提交与回滚)。

数据库和备份都含凭据及正文，应同等保护。运行中直接复制 `clawbot.db` 不能保证包含 WAL 中的数据，备份规则见[数据与产物](../design/sqlite-storage.md#临时文件与备份)。
