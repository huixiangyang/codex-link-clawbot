# 业务体系重整需求

状态：用户已确认个人远程工作台、单绑定、输入 24 小时／结果 7 天，并授权连续完成设计和业务重构。本文作为实施与验收基线。

现状依据见[产品与业务复核](../../docs/product/assessment.md)。

## 1. 问题与目标

用户需要从微信发起本机 Codex 工作，能够连续沟通、确认执行上下文、拿到完整成果，并在中断或发送失败时知道如何恢复。现有功能围绕存储、线程和状态展示展开，尚未支撑完整任务闭环。

已确认目标：个人自托管的 Codex 远程工作台。微信为主要请求入口，并通过单键数字菜单完成手机高频管理；Web 为完整搜索、结果查阅和详细管理入口，CLI 为本机配置和运维入口。

本轮不建设 Web 提交与排期平台。根据用户对手机输入和小屏阅读的明确要求，微信提供新的单键数字菜单，不沿用旧多位编号协议。

## 2. 核心用户故事与验收条件

### R1 首次使用与能力就绪

作为实例所有者，我需要知道现在能否发任务，以及缺什么配置。

- 当用户首次打开工作台时，系统应分别显示绑定、Codex、工作空间与可选输出能力的就绪状态。
- 当某项能力不可用时，系统应给出影响范围和明确下一步，不能把“程序在运行”直接当成“能够完成任务”。
- 当实例未配置语音或视觉渲染时，系统应拒绝保存不可用模式，并在页面解释原因。

### R2 连续会话与稳定上下文

作为微信使用者，我希望后续消息继续当前工作，而不是无意中丢失上下文。

- 当当前工作空间尚无目标会话且用户首次提交请求时，系统应建立当前会话；随后提交的消息应继续该会话。
- 当首次会话尚在创建、用户连续发送多条消息时，系统应立即拒绝第二条指令，展示原因与数字会话菜单，不创建等待任务。
- 当用户显式切换目标时，系统应仅影响切换后接收的新请求；当前执行不得随页面选择改变归属。
- 当已接收请求创建出线程时，系统不得覆盖用户后来选择的新目标。
- 当切换或创建目标失败时，系统应保留切换前的工作空间与会话组合。
- 当当前目标不在最近线程列表的第一页时，系统仍应正确显示当前目标。

### R3 可理解的请求中心

作为用户，我需要看见每条请求在哪里、执行状态如何，以及有哪些操作。

- 当请求即时接收成功时，系统应返回稳定编号、工作空间和目标会话；重复微信消息不得生成第二次执行。
- 当用户打开请求中心时，系统应区分进行中、需要处理、历史记录；分页或筛选不得使记录永久不可达。
- 当用户查看请求详情时，系统应显示输入摘要、上下文、创建/开始/结束时间、执行状态、投递状态、结果可用性及明确原因。
- 当用户提交操作时，系统应按服务端当前状态校验；旧页面不能取消另一条刚开始的请求。

### R4 执行结果与微信投递分开

作为用户，我需要知道“工作是否完成”与“消息是否送达”，以选择正确的恢复动作。

- 当 Codex 完成并生成回答时，系统应先可靠保存结果和产物，再开始微信投递。
- 当微信明确拒绝或返回不确定结果时，系统应保留执行已完成的事实，并独立标识投递失败或待确认。
- 当用户恢复投递时，系统不得重新调用 Codex 执行原任务。
- 当进程在执行中重启时，系统应标识执行中断，不自动重跑可能产生副作用的任务。
- 当进程在发送中重启时，系统应标识投递待确认，不自动重复发送或重跑。

### R5 查看结果与取回文件

作为用户，我需要在微信之外取回完成成果，也需要取回微信没能发送的文件。

- 当结果仍在保留期内时，系统应允许在认证后的 Web 页面查看回答、复制文字和下载产物，无论微信投递成功与否。
- 当用户下载产物时，系统应校验归属、文件类型、路径和完整性；只允许取回该请求已经登记的产物。
- 当入站图片、文件或消息令牌到期清理时，系统不得一并删除尚在结果保留期的回答与产物。
- 当结果即将或已经过期时，系统应展示到期时间与实际可用状态，不仅显示笼统的“可交付”。
- 输入保留 24 小时、结果保留 7 天、记录保留 30 天，并实施容量限制。

### R6 受控恢复与取消

作为用户，我需要从失败中恢复，同时避免重复工作和重复发送。

- 当执行失败或中断且输入仍可用时，系统应允许用户显式重新执行，创建新的请求并关联原请求，保留原始失败记录。
- 当执行已经成功而仅投递失败时，系统应优先提供查看结果、下载或重新投递，不把它当成执行失败。
- 当重新投递缺少可用的微信上下文时，系统应解释需要用户重新发送消息，并继续提供 Web 取回，不假造上下文令牌或声称已发送。
- 当相同恢复操作因网络重试重复到达时，系统应避免创建多条相同恢复请求。
- 当用户取消指定请求时，系统应校验请求编号和归属；进入结果收尾后不得再将已生成并发送的结果标记为取消。

### R7 会话管理与能力取舍

作为用户，我需要维护正在进行的工作，不需要理解全部 Codex 内部能力。

- 当用户进入会话管理时，系统应提供搜索、分页、新建、选择、改名与归档，并明确哪些会话可作为当前目标。
- 当会话不可访问、被归档或目录超出受信任范围时，系统应阻止将它作为新请求目标，并给出原因。
- 当用户选择回复模式时，系统应基于当前能力整体校验和保存偏好；不能先保存一半再报错。
- 当后台自动刷新状态时，系统不得覆盖尚未提交的会话或偏好表单。
- 分支、长期目标、评审、压缩、线程关系图不列为首轮验收项；是否保留实现应由明确使用场景与维护成本决定。

### R8 即时管理、排空与锁定

| 控制 | 业务语义 |
| --- | --- |
| 打断执行 | 只停止指定请求或原生轮次；旧菜单不能打断后续轮次 |
| 切换会话 | 随时改变新消息的目标；原执行继续回传结果 |
| 排空实例 | 停止新工作准入，等待当前工作收尾；恢复后没有待执行积压 |
| 锁定远程入口 | 拒绝新的微信工作；当前执行不隐式取消 |

同一会话忙碌时再次提交必须立即失败，说明未提交、不会稍后执行，自动展示实时会话操作菜单。不同会话互不阻塞。删除暂停、恢复队列、排序与移除等待任务的业务和接口。

### R9 绑定范围一致

作为实例所有者，我需要管理界面与实际接入范围一致。

- 实例只启用一个明确选定的微信绑定；多个有效凭据且未选择时拒绝启动。
- 切换绑定需要停服，未选中绑定的记录不会自动执行。工作台目标、执行记录、结果、偏好、锁定统一属于当前绑定。

### R10 手机单键操作与小屏阅读

- 首页只展示六项高频功能，输入单个数字完成选择；列表每页四项，固定翻页、首页与退出键。
- 会话、工作空间、会话状态、结果与回复设置必须能在微信完成，不要求用户改用网页。
- 一次导航只发一张紧凑图片；图片不可用时同编号文字仍可操作。
- 长结果每次只发一页，数字翻页；打断和恢复动作需确认具体对象。
- 数字绑定展示时的完整 ID；过期、重启和消息重投不得重复操作或误选目标。

## 3. 首轮功能边界

必须完成：R1–R6、R7 的基本会话维护与能力校验、R8、选定的 R9 方案。

首轮不做：团队权限、任务审批、定时调度、任意远程 Shell、完整复制 Codex 客户端。视觉质量遵循项目设计规范，但视觉扩展不能替代请求与结果闭环。

重整时删除被替代的旧业务入口与死分支，不新增兼容解释层。若需要改变存储格式，应另行定义明确的离线迁移或显式重置策略，不能在运行时猜测旧格式；升级必须备份与验证，不能擅自清空现有用户数据。

## 4. 业务验收场景

| 场景 | 预期结果 | 对应需求 |
| --- | --- | --- |
| 未手动建线程，连续发送“检查登录问题”和“继续修复” | 上一轮结束后继续同一会话；执行中第二条失败并弹出数字菜单 | R2 |
| A 正在执行时切换到 B | 原任务仍执行于 A，后续消息进入 B，迟到的 A 线程不抢占目标 | R2、R3 |
| Codex 成功，微信发送文件失败 | 显示执行完成、投递失败；Web 可以下载，不要求重跑 | R4、R5 |
| 成功回答已发往微信，稍后打开网页 | 在保留期内可以查看同一回答和产物 | R5 |
| 执行中进程重启 | 明确中断，用户查看上下文后决定是否重新执行 | R4、R6 |
| 发送中进程重启 | 原结果保留，提示检查微信是否已收到，不自动重复执行 | R4、R6 |
| 从旧页面取消请求 A，而 A 已结束、B 刚开始 | 返回 A 已不可取消，B 不受影响 | R3、R6 |
| 实例无语音提供商 | 页面明确不可用，接口也不能保存语音模式 | R1、R7 |
| 有超过 6 条请求、12 个线程、8 个文件 | 所有保留期内记录都可通过分页或筛选到达 | R3、R5、R7 |

## 5. 已确认的产品选择

个人远程工作台；单绑定；输入 24 小时、结果 7 天、记录 30 天。需求已获确认并授权实施，技术方案与执行项见[设计](design.md)和[任务](tasks.md)。

### R11 删除会话队列（2026-09-22 用户明确调整）

- 第二条指令在文本、图片、文件入口及重新执行入口均适用忙碌拒绝规则；准备输入时即占用会话。
- 拒绝回执先持久化再回复，不保存被拒正文或下载其附件。微信重投与重启均不能补执行原指令。
- 手机弹出紧凑数字菜单：1 刷新状态、2 打断本次执行、3 切换会话、4 新建对话；无法打断时不显示 2。
- 保留执行记录与结果取回，不将历史记录用作待执行列表。
- 离线迁移将旧等待记录标记为已取消且未执行，保留可核对的记录与原备份。
